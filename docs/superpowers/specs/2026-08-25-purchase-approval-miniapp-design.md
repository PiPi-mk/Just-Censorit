# 购买审批小程序设计文档

## 1. 文档信息

- 文档日期：2026-08-25
- 文档类型：产品设计文档 + 首版技术方案
- 产品名称：购买审批小程序
- 当前阶段：设计确认，待进入实施规划

## 2. 背景与目标

### 2.1 背景

用户希望做一个适用于熟人小群体互动的小程序，用于围绕“某样东西该不该买”发起审批。一个成员可以把自己的购买需求发布到所在群组中，群组内其他成员基于商品信息、预算影响和替代方案进行分析，并给出同意或不同意的意见。所有成员都能看到每个人的投票态度与理由，形成透明的群体决策过程。

### 2.2 产品目标

本产品的目标不是做一个普通投票工具，而是做一个“带理由的实名购买审批工具”，核心是：

1. 支持熟人群组内发起购买审批。
2. 支持成员围绕审批内容进行轻量分析。
3. 支持实名、透明、可追溯的投票公示。
4. 支持不同审批策略，降低争议。
5. 支持对历史审批结果进行回看。

### 2.3 核心价值

- 对发起人：获得来自熟人群体的集体建议，而不是单纯靠自己拍板。
- 对群组成员：能够看到完整背景信息，并基于自己的判断给出意见。
- 对整个群组：形成透明、有记录的共同消费决策机制。

## 3. 用户与场景

### 3.1 目标用户

- 朋友小群体
- 宿舍群体
- 社团或兴趣小组
- 有共同消费决策需求的熟人组织

### 3.2 核心使用场景

- 某成员想买一件数码产品，想听群里朋友意见。
- 某小组要采购共享物品，希望大家投票决定是否购买。
- 某成员在预算有限时，希望群组帮忙判断是否值得买。
- 某群体要做集体采购，需要先在组内透明讨论和表决。

## 4. 产品定位

### 4.1 产品定位

一个面向熟人小圈子的“购买审批 + 集体建议”微信小程序。

### 4.2 首版产品形态

首版采用“轻量审批型”方案，以最短路径完成：

建组 -> 发起审批 -> 成员实名投票并附简短理由 -> 规则结算 -> 结果公示

### 4.3 不做的事情

首版不追求做成复杂社区，不引入过重的互动机制，包括：

- 不做多轮评论回复链
- 不做点赞、排行、积分体系
- 不做匿名投票
- 不做跨群传播
- 不做多级审批流

## 5. 角色定义与权限

### 5.1 群主

权限包括：

- 创建群组
- 生成邀请码
- 管理群成员
- 控制是否允许新成员加入
- 在“群主裁定”规则下给出最终审批结论

### 5.2 普通成员

权限包括：

- 通过邀请码加入群组
- 查看所属群组内的审批
- 发起购买审批
- 对审批投同意或不同意票
- 填写简短理由
- 查看所有成员的投票结果和理由

### 5.3 审批发起人

审批发起人是普通成员的一个特殊身份，在某条审批中拥有额外能力：

- 创建并发布审批
- 补充审批说明
- 在规则允许范围内提前结束审批
- 查看该审批的详细进展和最终结论

### 5.4 系统

系统负责：

- 记录审批数据
- 记录投票数据
- 实时统计同意/反对票数
- 根据审批规则产出结论
- 公示最终结果

## 6. 核心业务规则

### 6.1 群组规则

- 群组由群主创建。
- 用户通过邀请码加入群组。
- 审批严格归属于某一个群组，不跨群显示。
- 只有群组成员可以查看该群组内的审批数据。

### 6.2 投票规则

- 每个成员对同一审批只有一个当前有效投票。
- 投票选项为“同意”和“不同意”。
- 投票时允许填写简短理由。
- 首版默认允许改票，系统始终保留每个成员最新的一次投票结果。
- 所有投票均为实名展示，不支持匿名。

### 6.3 透明规则

- 所有群成员都能看到谁同意、谁不同意。
- 所有群成员都能看到每位投票成员填写的简短理由。
- 结果公示页必须展示统计结果和实名名单。

### 6.4 判定规则

审批创建时必须绑定一种判定策略，发布后不可修改。首版支持以下策略：

1. 多数票通过
2. 全员同意
3. 群主裁定
4. 仅供参考

#### 多数票通过

- 同意人数大于不同意人数，则审批通过。
- 若同意人数小于等于不同意人数，则审批未通过。
- 平票按未通过处理。

#### 全员同意

- 所有已投票成员都投同意，且不存在反对票时，审批通过。
- 只要存在反对票，则审批未通过。

#### 群主裁定

- 群成员投票结果仅作参考。
- 截止后由群主手动点击“通过”或“不通过”。

#### 仅供参考

- 系统只展示投票分布和理由，不自动给出“通过/未通过”硬结论。
- 最终是否购买由发起人自行参考决定。

## 7. 审批单设计

### 7.1 审批单目标

审批单既要支持快速发起，也要保证成员能做出相对有依据的判断。因此表单采用“分析版”字段，而不是极简版字段。

### 7.2 审批单字段

#### 基础信息

- 审批标题
- 商品名称
- 商品图片
- 商品链接
- 单价
- 购买数量
- 预估总价

#### 发起理由

- 为什么想买
- 当前痛点
- 预期收益

#### 分析信息

- 预算影响
- 替代方案
- 不买的风险

#### 规则设置

- 判定策略
- 截止时间
- 是否允许改票

#### 系统归属信息

- 所属群组
- 发起人
- 创建时间
- 发布时间

#### 结果信息

- 当前同意人数
- 当前不同意人数
- 已投票人数
- 未投票人数
- 最终结论
- 结论生成时间

### 7.3 字段设计原则

- 审批标题独立保留，不直接等同于商品名称。
- 单价和总价分开存储，便于展示与统计。
- 截止时间为首版必填项，避免审批长期悬挂。
- 判定策略为必填项，避免后续争议。
- 是否允许改票为首版显式开关，但默认建议开启。

## 8. 页面结构设计

### 8.1 首页 / 我的群组

功能包括：

- 展示我加入的群组
- 创建群组
- 输入邀请码加入群组
- 切换当前群组

设计原则：

- 首页只承载群组入口，不混入审批详情信息。
- 把“进入哪个群组”作为第一步，避免信息混乱。

### 8.2 审批列表页

功能包括：

- 展示当前群组下所有审批
- 展示审批状态标签
- 支持查看进行中、已结束、我发起的、我参与的审批

每条审批卡片建议展示：

- 审批标题
- 商品名称
- 发起人
- 判定策略
- 截止时间
- 当前票数概览
- 当前状态

### 8.3 发起审批页

功能包括：

- 填写审批单字段
- 上传商品图片或粘贴商品链接
- 选择判定规则
- 设置截止时间
- 设置是否允许改票
- 保存草稿或直接发布

### 8.4 审批详情页

这是首版最核心的页面，建议同页承载：

- 审批基础信息
- 发起人理由和分析信息
- 投票区
- 同意/不同意票数统计
- 实名结果区
- 成员理由列表

设计原则：

- 用户在一个页面里完成“了解情况 -> 做决定 -> 查看他人意见”。
- 不把信息打散到过多子页面，减少跳转成本。

### 8.5 结果公示页

功能包括：

- 展示最终结果
- 展示采用的判定规则
- 展示票数分布
- 展示实名同意名单和反对名单
- 展示群主裁定结果或参考型结论说明

说明：

首版中，结果公示页可以是审批详情页中的一个结果模块，不强制做成重页面。

## 9. 状态流转设计

### 9.1 审批状态

首版仅保留以下 5 个状态：

1. 草稿
2. 进行中
3. 已截止
4. 已通过
5. 未通过

### 9.2 流转规则

- 草稿 -> 进行中：发起人点击发布
- 进行中 -> 已截止：到达截止时间，或发起人提前结束
- 已截止 -> 已通过：系统根据规则判定结果为通过
- 已截止 -> 未通过：系统根据规则判定结果为不通过

### 9.3 状态设计原则

- 首版不增加“撤回”“作废”“回退”“复审”等复杂状态。
- 若用户要重新讨论，建议复制旧审批再创建一条新审批，而不是回退原审批状态。

## 12. 技术方案

### 12.1 技术形态

推荐采用：

- 微信小程序前端
- 独立后端 API
- 关系型数据库

### 12.2 前端技术建议

推荐方案：

- Taro
- React
- TypeScript

推荐原因：

- 页面和组件组织清晰
- 状态管理和接口集成成熟
- 后续如需扩展 H5，迁移成本更低

备选方案：

- 微信原生小程序
- uni-app

### 12.3 后端技术建议

后端可采用任一熟悉的主流栈，关键是模块清晰。推荐按能力拆分：

- 用户模块
- 群组模块
- 审批模块
- 投票模块
- 规则结算模块

### 12.4 前端模块划分

- auth：登录态、用户信息、当前群组缓存
- group：群组列表、建组、入组、成员展示
- approval：审批列表、审批详情、发起审批、状态展示
- vote：投票、改票、理由提交、实名名单展示
- result：规则说明、统计、最终结果展示

## 14. 接口设计建议

### 14.1 群组相关

- POST /groups：创建群组
- POST /groups/join：通过邀请码加入群组
- GET /groups/my：获取我的群组列表
- GET /groups/{groupId}/members：获取群成员列表

### 14.2 审批相关

- POST /approvals：创建审批
- GET /groups/{groupId}/approvals：获取群组审批列表
- GET /approvals/{approvalId}：获取审批详情
- POST /approvals/{approvalId}/publish：发布审批
- POST /approvals/{approvalId}/close：提前结束审批

### 14.3 投票相关

- POST /approvals/{approvalId}/vote：提交或更新投票
- GET /approvals/{approvalId}/votes：获取审批投票列表

### 14.4 结果相关

- GET /approvals/{approvalId}/result：获取审批结果
- POST /approvals/{approvalId}/owner-decision：群主裁定结果

## 15. 安全与约束

### 15.1 权限约束

- 只有群组成员可以访问本群审批数据。
- 非群主不能执行群主裁定操作。
- 非审批发起人不能提前关闭他人审批，除非后续补充管理权限。

### 15.2 数据约束

- 审批发布后 rule_type 不允许修改。
- 截止后不能新增投票。
- allow_revote 为 false 时，用户投票后不可再次变更。

### 15.3 可审计性

- 最终结论需记录判定依据。
- 群主裁定场景建议记录 decision_reason。
- 重要状态变更应保留时间戳。

## 18. 结论

该产品首版应聚焦于“实名透明投票 + 可配置规则 + 购买场景分析”三件核心能力，不追求功能繁多，而是先确保基础闭环顺畅、规则清晰、展示透明。只要将审批发起、实名投票、结果判定这三部分做扎实，产品第一版就具备明确的独立价值，并能为后续评论、提醒、统计等扩展能力打下清晰基础。
